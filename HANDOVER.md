# Handover

## Status

Playable Quoridor on the open-source-hands game starter: 9×9, ten fences each, orthogonal steps, straight jumps, diagonal jumps, fence overlap, crossing, and a path check for both pawns. Versus a heuristic, or two people on one machine. Camera, mouse, touch and keyboard all meet in one hand. A bot plays through the real gesture engine.

## What works, and how it was verified

- `npm test`: 70 tests. Rules, heuristic, grab latch, palm roll, synthetic gestures, both 3D camera projections, furniture support/layout, low fixed-slot coffers, and reference-image homography/hit regions. Input tests use actual landmarks through the real engine for both hands: fingertip aiming, release with the other fingers still curled, no fist pickup, and pointer stability while pinching.
- `npx tsc --noEmit` passes.
- `npm run mouse` against the dev server: drag the pale pawn one square, place a fence, turn it with R, turn it back with the right button. No console errors.
- `npm run capture`: the bot plays a game (it misses once on purpose), the machine wins in 24 moves, the bot pinches to restart. No console errors and no `GL_INVALID`. Screenshots in `captures/` were looked at, including a phone-sized board.
- `npm run loud` while the bot plays: p90 −30.1 dBFS, peak −22.9 dBFS.
- 2026-11-14 recheck: build and all 33 tests passed. `npm run pinch` exercised the real browser input/engine/game chain with synthetic landmarks: pawn pickup, pinch begun over empty space then moved onto a pawn, two-finger release despite midpoint movement, fence placement, and lost-hand cancellation. `npm run mouse` passed drag and rotation; `npm run capture` finished in 24 moves and restarted with no console errors. Desktop screenshots were inspected. Chrome was selected with `CHROMIUM_PATH`; these are synthetic-input checks, not a real webcam test.

## Not verified

- A real webcam, by a person. Only synthetic hands and the pointer drove it.
- Listening by ear. The loudness numbers above are from the analyser, not from speakers.
- A real phone, Safari, or Firefox. The phone check was a 390×844 headless viewport.
- Native DPR2 and sustained performance with a real webcam running. The earlier object-only study scene measured ~65.3fps, p95 16.8ms on Intel UHD/ANGLE D3D11 with a 2-million-pixel budget (requested DPR2 becomes ~1.242 at 1440×900). Those figures and older llvmpipe samples do not measure the new table/chair scene. Visual-script startup fps is not a sustained benchmark.

## Tuning knobs

| Constant | File | What it does |
| --- | --- | --- |
| `PINCH_GAP_ON`, `PINCH_GAP_OFF` | `src/hand-pointer.ts` | normalised thumb/index gap hysteresis (0.28 / 0.42) |
| `RELEASE_HOLD_S`, `LOST_GRACE_S` | `src/grab.ts` | release grace (120 ms), lost-hand cancellation (120 ms); pickup is immediate |
| `ROLL_TO_H`, `ROLL_TO_V` | `src/grab.ts` | palm-roll dead zone used by the synthetic bot |
| `margin` (0.12 cell) | `fenceOrientation` in `src/scene.ts` | camera fence gap-direction hysteresis |
| fence cap (`spent >= 2`) | `src/ai.ts` | the machine blocks at most twice, and only when the other pawn would finish next turn |
| `REGION` | `src/input.ts` | the part of the camera image that maps onto the screen |
| pawn radius 0.52, cell snap 0.72, slot snap 0.78 | `src/scene.ts` | how generous a grab and a drop are |
| master gain 1.05 | `src/audio.ts` | overall loudness |

## Design decisions and why

- Rules stay in grid cells, with no three.js, so the tests and the bot can run them. The scene turns a screen point into a cell with a ray onto the board plane.
- Mouse, touch and the bot are synthetic landmarks through the real engine. There is one grab latch.
- A thumb-and-index pinch picks up a piece; separating the fingers places it. Threshold hysteresis and timing gates reduce accidental drops.
- Follow the shipped GODHAND interaction method: geometric thumb/index gap, palm-scale normalization, fingertip-vs-joint and index-reach guards, and a grip offset frozen in palm-local coordinates while closing/pinching. Do not gate pickup on a pose score or add a dwell/minimum-carry timer. Keep the copied kit unmodified. Unlike GODHAND’s raw-input processor, this game consumes the kit’s filtered landmarks, so it adds no second cursor filter.
- A refused drop puts the piece back and does not spend the turn.
- The machine walks a shortest path and spends at most two fences, both of them to stop a pawn that would score next turn. A wider search made games that never finished; two blocks still punish a naked race.
- Stacks sit beside the board on a wide screen and on the baselines on a tall one, so a phone can still reach its fences.
- No post-processing or remote art assets. Shadows are cached while the board is static, and invalidated for pawn/fence/stock/carry changes and resize/presentation changes. Reflection environment is assigned only to ceramic and metallic materials. The 3D backing buffer is limited to 2 million pixels; DOM UI retains native resolution.

## Gotchas

- While the left button is down, Chromium does not deliver a right-button `pointerdown`. It delivers `contextmenu` only. `src/input.ts` turns the fence from that, and ignores the menu when the pointer event already counted.
- Camera fence orientation is selected from board gaps, never from hand roll. Only the synthetic bot uses `features.roll`; mouse/touch retain manual controls. Near a crossing, aim a little along the desired gap to choose that direction.
- The bot's first carry is a deliberate miss, so the red preview and the refusal get exercised. It then plays the heuristic.
- Headless frame times on llvmpipe are not the game's frame times on a GPU.
